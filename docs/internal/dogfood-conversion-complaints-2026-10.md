# dogfood で不満だった変換の調査記録（2026-10）

> Last updated: 2026-10-19（方針案 1・2・3 を実装: ADR-036 / ADR-037）

ADR-035（左文脈の引き継ぎ）インストール後、ユーザーが不満に感じた変換をその場で報告し、ログから原因を調べて記録する。この文書は記録であり、修正の着手は別途判断する。

ログの読み方: `~/.gyaim/gyaim.log` の `Commit outcome`（確定ごとの順位と文脈）と `Fast context accepted detail`（候補一覧、モデルの採点 `review.scores`、学習頻度 `dictionaryCandidates[].studyFrequency`）を突き合わせる。並べ替えの式は ADR-032: `total = 平均logprob + 2.0 × log2(1 + 学習頻度) + 2.0 × ContextDict affinity`。

## ケース 1: ikou → 以降 が 移行 に負ける（2026-10-13 09:10）

報告: 「これ更新されたら最後に取得したやつ以降のものが一通り」の候補リストが不満。ghostty、controller F1FCBEA6、全確定で `contextInherited=true`。

| 時刻 | 文脈（モデル入力の末尾） | モデル平均 logprob | 学習頻度 | 式の合計 | 表示先頭 | 確定 |
|---|---|---|---|---|---|---|
| 09:10:10 | 更新されたらそれ | 以降 −0.005 / 移行 −2.70 | 以降 10 / 移行 38 | 以降 6.91 / 移行 7.87 | 移行 | rank1 移行（誤り、未修正） |
| 09:10:20 | 取得したやつ | 行こう −0.49 / 移行 −0.51 / 以降 −0.54 | 移行 39 | 移行 先頭 | 移行 | rank2 以降 |

1 回目はモデルが 以降 をほぼ確信していた（差 2.7）が、学習頻度の差（log2(39) − log2(11) = 1.83、重み 2.0 で 3.65）が上回った。誤確定で 移行 の頻度が 38→39 に増え、2 回目はさらに不利になった。

同型の過去事例: 2026-09-29 15:48（文脈「時」、モデル差 3.59、移行 を確定）、2026-10-06 13:40（モデル差 0.82、以降 を選択）。

## 伺い知れること

- モデルの明確な判断を学習頻度の重みが覆している。AI 主体方針（ADR-032）の意図から外れる挙動。
- 一律に重みを下げる解は採れない。llm-ranked 以降の全ログで「頻度がモデル先頭を覆した」非ひらがな事例 173 件のうち、ユーザーが頻度側を確定したのが 142 件、モデル側が 24 件。頻度側が正しかった例: 私/渡（差 9.6）、件/県（差 6.1）、側/川、機能/昨日。
- モデル先頭の絶対スコアでも切り分けられない。絶対値 −0.05 以上の 20 件でも頻度側確定が 16 件（済/済み、休/休み、気持/気持ち のような語幹切れが大半）。
- 重みの両立不能: BUG-036（君31/キミ7、モデル差 3.4）を守るには重み 1.7 以上、この ikou を通すには 1.48 未満。線形の重みでは両方は満たせない。
- 両候補ともユーザーの常用語で、文脈で決まる同音異義語。本来は ContextDict の affinity が効くべき場所だが、両ケースとも 0 だった（それ→以降、やつ→以降 の学習が無い）。
- 未修正の誤確定が study 頻度を増やす自己強化（移行 34→38→39）。
- 「頻度側を確定」が正解とは限らない。1 回目の ikou も確定上は頻度側だが誤変換なので、上の 142 件には同種の未修正誤変換が混じる。

## 付随観察（同じ文）

saretara、sita、yatu、sibaraku は `kana-hiragana` 経路で heuristicRank 2〜3（先頭は 下/奴/暫く 等）。ひらがな確定が学習されない問題（別途提案済み）と同根。

## ケース 2: okimasita → おきました が 起きました に負ける（2026-10-14 17:02）

報告: 「再度レビューリクエストを送っておきました」の okimasita が微妙だった。ghostty、controller 7F5A927B、文脈「再度レビューリクエストを送って」。

| 候補 | モデル平均 logprob | 加減点 | 合計 | 表示順 |
|---|---|---|---|---|
| おきました | −0.00 | 入力ひらがなの減点 −3.0 | −3.0 | 3 |
| 起きました | −1.34 | study 頻度 1 → +2.0 | +0.66 | 1 |
| 置きました | −1.28 | なし | −1.28 | 2 |

17:02:38 に rank1 の 起きました を確定（誤り）。17:02:41 に打ち直して `kana-hiragana` 経路で おきました を確定（表示 4 番目）。この誤確定で studydict の 起きました は頻度 2 になり、次回の加点は +3.17 に増える。打ち直しの おきました は学習されない。

### 伺い知れること

- モデルは「送って＋おく」の補助動詞をほぼ確信していた（−0.00、2 位との差 1.28）。ADR-032 の「入力のひらがなそのものは先頭に出さない」固定減点 3.0 がそれを打ち消した。
- 固定減点そのものは集計上は正しい。llm-ranked 以降の全ログで、モデルがひらがなを先頭にした 467 件のうちユーザーが漢字を選んだのが 438 件（ところ/所、いま/今、のと/能登、ほか/他 など）。差 2.0 以上に絞っても漢字 34 件、ひらがな 15 件。減点を外すと悪化が多い。
- モデルが正しくて抑え込まれた側（15 件）は した、された、すれば、されている、つまり、ありがとう のような活用形・接続語で、今回の おきました と同じ系統。漢字が勝った側は 所/今/他/能登 のような名詞・副詞が多い。品詞で傾向が分かれている可能性があるが、未検証。
- 1 位になったのは減点の結果ではなく、誤学習の 起きました（頻度 1）への +2.0 が決め手。頻度 1 の語に 2.0 の加点が付く設計は、一度の誤確定を次回の既定にしてしまう。
- かな確定（`kana-hiragana`）が学習されないため、誤りだけが蓄積して正解は蓄積しない。ケース 1 の自己強化と同じ構図で、こちらは初回の誤りから始まる。
- 設計上の前提: ADR-032 は「ひらがなはかな確定キー（現設定では `;` / F6 / Ctrl+Shift+U）で常に出せる」として固定減点している。かな確定は既定で学習しない（`kanaConfirmStudyEnabled=false`）ので、補助動詞のようにひらがなが毎回正解の語は「毎回 1 打多い」状態で固定され、誤確定の漢字だけが学習される。
- 分析スクリプト: scratchpad の `kana_top.py`（セッション a226e94b）。

## ケース 3: 候補ウィンドウがキャレットから離れた位置に出る（2026-10-15 11:39）

報告: 「定期的にカーソルの位置と候補リストの吹き出しの位置がおかしくなる」。スクリーンショットでは Chrome の Google Docs でキャレットは本文の右下（「そんなに出ないと思っている」の直後）にあるのに、候補ウィンドウ（同じ 思う 思っている …）は Chrome ウィンドウの左上、タイトル「保守定例議事メモ」のすぐ下に出ている。同時刻のログは controller D1205611、入力 omotteiru、`contextInherited=true`。

### 分かっていること

- 位置決定は ADR-018（`CandidateWindowPositioner.resolveLineRect`）。クライアントが返す rect が「原点付近（x, y < 64）かつ幅 2px 以下」のときだけ疑わしいと見なし、前回正常値かマウス位置に退避する。それ以外は返された rect をそのまま信用する。
- 今回の表示位置はウィンドウの左上なので、x は小さく y は大きい rect が「妥当」と判定されて使われた可能性がある（例: Chrome がウィンドウ内ローカル座標や上下反転した座標を返した）。ただし未確認。
- 位置のログ `showWindow: reportedLineRect=… resolvedLineRect=… source=…` は debug レベルで、`gyaim.log` にも unified log にも残っていない（`log show --debug` で該当時刻を引いても 0 件）。このため今回の reportedLineRect は取れない。
- 既知の類例は Issue #10（Cosense で左下に出る、ADR-018 で対処済み）。Google Docs での左上は別パターン。

### 伺い知れること

- ADR-018 の疑わしい rect の判定は Issue #10 で観測した「原点付近」の形にだけ合わせてあり、Google Docs の返す値がそれと違う形なら素通りする。
- 再現時の reportedLineRect が無いと判定条件を広げる根拠が作れない。次に起きたときに値を取る手段が要る（候補: showWindow のログを info に上げて gyaim.log に残す、または再現中に `log stream --predicate 'subsystem == "com.pitecan.inputmethod.SwiftyGyaim"' --level debug` を流しておく）。
- 「定期的に」という報告なので、Google Docs 側で IME 用の隠し入力要素の位置が一時的にずれる（スクロールやレイアウト更新の直後など）可能性もある。これも未確認。

加えて、先頭確定の直後 15 秒以内に同じ読みを別の語で打ち直した「隠れ miss」が 7 件（kanketu、siyou、okimasita、kisoku、kuroeda、miyabe、[）。miyabe は外部候補（ゲーラブタスク一覧）を誤って確定している。

外部候補全体: 表示 119 回、選択 61 回、辞書語を押し下げた 58 回。長さで線引きしても 5 分 5 分（10 文字以下を残すと選択 40/61 を守り押し下げ 41/58 を解消）。

### 方針案（優先順。1〜3 は 2026-10-19 に実装 — ADR-037、showWindow info ログ、ADR-036 の (a)+(b)。(c) は選択時刻がログに無く効果を見積もれないため見送り）

1. 打ち直しによる学習の取り消し。同じコントローラで同じ読みを 15 秒以内に別の語（かな確定を含む）で確定し直したら、直前の確定で増えた study 頻度を戻す。ケース 1・2 の自己強化（移行 34→39、起きました 1→2、使用 39→41）を止める唯一の対症で、heuristic を増やさず学習データ側を正す。WordSearch に取り消し API が無いので追加が要る。
2. 候補ウィンドウ位置の記録。`showWindow:` の reportedLineRect / source を info に上げて gyaim.log に残す。ケース 3 の判定条件を決める材料集めで、挙動は変えない。
3. 外部候補の位置。辞書の exact 候補がある場合は外部候補をその後ろ（2 番目）に置く。押し下げ 58 件が先頭になり、選択 61 件は番号キー 2 になる。利得は小さく、元の Gyaim の登録ワークフロー（外部候補が先頭）を崩すので、ユーザー判断。
4. 学習頻度の重み（ケース 1）は変えない。一律変更は悪化が多く（173 件中 142 件は頻度側が正解）、1 の取り消しと ContextDict で様子を見る。
5. モデルが外す同音異義語（事由、簡潔、毀損、私用）は辞書やルールで直さず、モデル側（学習データ）の課題として別建てにする。

### 方針案 3（外部候補）の補足

外部候補はクリップボード（コピー後 5 秒以内）と選択テキスト（時間制限なし）を raw 入力の直後に置く（ADR-008）。確定するとユーザー辞書（localdict.txt）に `読み→文字列` で登録される。誤確定が最優先辞書に残り、localdict.txt（412 行）に `ika→ssessing OpenSSH network access restrictions`、`tuiki→auth-severのタスクの…`、`siteki→元は #1917 と…`、`rei→Javaの開発者が…` のような行がある。

案: (a) 辞書の exact 候補があれば外部候補を 2 番に置く、(b) 並びは変えず長文・複数行の外部候補は確定しても登録しない、(c) 選択テキストにも 5 秒制限を付ける（選択時刻はログに無く効果は未確認）。(b) は副作用の修正として独立に価値がある。

分析スクリプト: scratchpad の `week.py`、`misscause.py`、`redo.py`（セッション a226e94b）。

## 再現方法

ケース 1: `Fast context accepted detail` を全ログ（`~/.gyaim/gyaim.log*`、`~/.gyaim/archive/*.log`）から読み、`kind=exact` かつ非ひらがなの候補について `review.scores` 単独の先頭と、上の式で学習頻度を加えた先頭が異なる確定を抽出する。確定語は `top[]` の `rank == chosenRank`。

ケース 3: 未再現。再現時に debug ログの `showWindow:` 行を取得する必要がある。
